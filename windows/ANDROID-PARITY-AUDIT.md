## Android HDR and smoothing: what the code actually does

Evidence: [PlayerScreen.kt](https://github.com/deep2093/SmbVideoPlayer/blob/177c110dce97f433686b33c7ca4096a0c8980925/app/src/main/java/com/deepak/videolibrary/player/PlayerScreen.kt), [NativeSvpEffect.kt](https://github.com/deep2093/SmbVideoPlayer/blob/177c110dce97f433686b33c7ca4096a0c8980925/app/src/main/java/com/deepak/videolibrary/player/NativeSvpEffect.kt), [JNI bridge](https://github.com/deep2093/SmbVideoPlayer/blob/177c110dce97f433686b33c7ca4096a0c8980925/app/src/main/cpp/native_svp_stream.cpp), [renderer](https://github.com/deep2093/SmbVideoPlayer/blob/177c110dce97f433686b33c7ca4096a0c8980925/app/src/main/java/com/deepak/videolibrary/player/NativeSvpRenderersFactory.kt).

1. Smoothing is opt-in (`experimental_smooth_60fps`, default false). Its target is hardcoded **60 FPS**, not 75/90/120. A preferred 60 Hz mode request is separate from generating pixels.
2. The native Media3 effect reads decoded textures, converts through YUV, feeds a look-ahead native stream and publishes frames at 1/60-second timestamps. The JNI bridge calls separately built **open-svpflow**, an open-source reimplementation, not the proprietary commercial SVP distribution. Native libraries are loaded conditionally; their presence and device support matter.
3. When native libraries are unavailable, `SmoothVideoView` is the legacy motion-estimation/warping path. It has motion-confidence/strength controls. `MotionFrameTiming` explicitly only plans timing; it must not be cited by itself as interpolation.
4. Native processing levels fit within 720p / 900p / 1080p / 1440p, preserving aspect and avoiding enlargement before interpolation. “Max/sharp” can enlarge/sharpen a lower processed frame; that is not full-resolution 4K motion estimation.
5. GPU/OpenCL and CPU backends exist. Adreno defaults conservatively to CPU unless the GPU path is opted into; CPU 1080p and GPU maximum quality have saved synthetic paced checks. Runtime counters and thermal/watchdog logic can lower/raise quality. After limited recoverable retries, failures rebuild ordinary playback for that file. These mechanisms do not certify all devices.
6. Source rates above roughly 61 FPS bypass the 60 FPS engine and request the fastest display. With smoothing off, Media3 avoids the effects pipeline to retain high-FPS throughput.
7. Normal HDR/PQ/HLG/Dolby-tag detection selects a SurfaceView/HDR window route. The renderer supplies missing PQ base-layer color info for selected Dolby Vision profiles when there is no DV decoder. This is **not** full Dolby Vision dynamic-metadata/profile-5 support.
8. HDR smoothing is another opt-in experiment (`experimental_hdr_smoothing`, default false). It PQ-encodes linear BT.2020 textures into an **8-bit** engine path and converts back to half-float linear output. Possible banding/precision loss and profile-specific color behavior remain; do not call this untouched 10-bit HDR interpolation or HDR10+/DV metadata preservation.

## Windows phase 1 implemented in this branch

- Persisted Off / Auto / 60 / 75 / 90 / 120 FPS choices, default Off, with per-choice unavailable reasons in native Playback settings.
- Capability reads from **running libmpv**, not a fabricated GPU score: current GPU VO, active hardware decoder, source FPS and display Hz. The hardware-decode requirement is deliberately conservative and may exclude easy software-decoded clips. It is not GPU throughput qualification.
- Auto requests mpv temporal blending at the active display cadence. A fixed choice requires a matching active refresh within 1% (59.94/60 and 119.88/120 are accepted). A 144 Hz monitor does not unlock a fictitious independent 120 FPS conversion. Change Windows display mode to 120 Hz or use Auto.
- Uses `interpolation=yes`, `video-sync=display-resample`, `tscale=oversample`; reserves extra decoder surfaces before the file loads. No `fps` duplication filter, source-FPS lie, display-FPS override, expensive spatial shader pack or mandatory CPU copy-back filter is installed. mpv display sync can make small audio/video clock corrections; passthrough outputs may prevent activation.
- Status says **requested**, identifies temporal blending and separately reports whether display sync is active. It is not a measured synthesized-frame counter. Ordinary frame repetition at a high display refresh is not optical flow either.
- Unknown capability, software decoder/non-GPU VO, lower/unknown refresh, HDR transfer, source at/above display FPS, unsupported player settings or sustained player-reported drops bypass smoothing. HDR output/color settings stay under existing mpv behavior pending validation.
- Eight-second grace period after reset/pause/seek/cache wait; three consecutive sampled intervals with at least three drops each latch a per-file fallback. Reopen the video or explicitly reset the setting to retry. This is a coarse performance safeguard, not proof of stall-free 4K. Unknown counters cannot certify performance.
- The Canvas, HWND, fullscreen owner, keyboard bindings, close order, native DLL provenance and MSI UpgradeCode remain intact. Runtime polling runs off the UI thread. Existing Unicode/artwork/collection fixes remain ancestors.

## Feasible engine paths and tradeoffs

| Path | What it provides | Hardware/performance and integration | Licensing/distribution |
|---|---|---|---|
| libmpv temporal scaler (implemented) | Temporal resampling/blending to display cadence; can reduce judder, can blend/ghost. **No motion vectors/optical flow.** | Stays in existing GPU renderer with hardware decode. No arbitrary independent target output FPS. Ordinary spatial GLSL upscalers do not add a motion-estimation pipeline. | Existing bundled libmpv terms/notices; no added external engine. |
| open-svpflow adapter (research next) | Motion-compensated synthesis conceptually closest to Android native backend. | Windows x64 build/API/stride/timestamp/cancellation integration still needed. Its Android arm64 JNI/effect cannot simply be copied into libmpv. Must verify backend and decoded-frame transfer costs. | Upstream advertises Apache-2.0; pin and audit exact source/dependencies rather than equating it with SVP commercial binaries. |
| SVP + VapourSynth/mpv | Motion-vector interpolation, target/quality controls; established optional ecosystem. | Needs compatible mpv filter build, plugins/runtime and frame access; hardware decode copy-back/filter transfers can cost substantial 4K bandwidth. CPU-only interpolation competes with decoding; GPU support still needs qualification. External-manager integration can be user-installed first. | SVP Free is freeware and Pro commercial; component terms differ. Do not bundle proprietary DLLs under SkyWing's GPL merely because an SVP installation works locally. |
| RIFE via compatible filter/runtime | Neural intermediate-flow synthesis; often better complex motion, still artifacts/scene-cut failures. | ncnn/Vulkan or NVIDIA TensorRT; VRAM, resolution, multiplier and model dominate. 4K60 is already high-end territory in SVP's published estimates; 4K90/120 must be measured, never promised. Lower interpolation resolution compromises detail. | Research RIFE repo is MIT; independently pin model weights, wrappers, ncnn/TensorRT and redistribution terms. ## Validation and practical test plan

Automated: policy cases for matching/fractional/unsupported display rates, unknown capability, software decode, HDR and high-FPS bypass; sustained-drop latch and pause/seek/counter-reset warmup; existing Windows scale, library, artwork, UTF-8, real libmpv fullscreen/controls and process-exit tests. Hosted CI's software GIF fixture tests native property reads and bypass, **not** hardware smoothing quality. CI also packages EXE/MSI, verifies pinned DLL/legal payload and archives matching Windows source.

Manual matrix (pending; record GPU/driver/Windows build, display mode, source codec/bit depth/resolution/rate, and screenshots of status):

1. Windows 10 and 11 x64; Intel/AMD integrated plus NVIDIA/AMD dedicated GPU where available. Install the previous preview, save shares/library/history/art, install the new MSI in place, verify one app entry and data retention. Check uninstall/reinstall separately using a disposable profile.
2. Local and UNC/mapped-drive H.264/HEVC/AV1 at 1080p and 4K, 23.976/24/25/29.97/30/50/59.94/60/90/120 FPS. Include Unicode paths, long names, queue switches and unavailable shares.
3. Start Off, establish ten-minute 4K baseline; then Auto. Compare player drop counters, responsiveness and lip sync. Do not label display refresh as generated FPS. Test 59.94/60/75/90/119.88/120/144 Hz where supported; fixed choices must wait on mismatched modes. Move between monitors and test a window spanning two displays.
4. Force software decoding with unsupported media and verify bypass. Test missing/unknown display information and audio passthrough: UI must report inactive display sync. Induce sustained drops and verify automatic bypass without stopping playback. Pause/seek/cache waits must not falsely trip it.
5. Repeat F/Esc at least 20 times with Canvas and control focus, held F, maximized restore, Alt-Tab, monitor move, Stop, next/previous and window close while decoding. Verify no invisible window/background process and unchanged HWND behavior.
6. Test SDR/HDR10/HLG/Dolby Vision samples on SDR and HDR displays with Windows HDR on/off. Phase 1 should bypass HDR smoothing; assess normal tone mapping/output separately. Verify color/black level/bit-depth with reference patterns before enabling future HDR interpolation.
7. Exercise every player control, file drop/Open With, rename, thumbnails, cover choice, scan, virtual/custom/original hierarchy and artwork review; check 100/150/200% DPI and small windows. Preserve known limits as reported defects rather than calling CI a complete acceptance test.

Build result links and exact test totals are recorded in the draft PR once CI completes. No physical 4K/HDR, user-network, display-mode or in-place MSI acceptance is claimed by this audit.
